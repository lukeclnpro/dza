CAHIER DES CHARGES TECHNIQUE — SITE DE TRADING FACTICE
===============================================================

STATUT DU PROJET
----------------
Nom de projet : SIMTRADE
Nature : plateforme de trading entièrement fictive / simulation
Objectif : reproduire l'expérience utilisateur d'une plateforme de courtage moderne
sans connecter de fonds réels, sans exécuter d'ordres réels et sans interaction
avec un marché financier réel.

IMPORTANT :
- Toutes les données financières sont simulées.
- Aucun dépôt réel, retrait réel ou transfert bancaire réel.
- Aucun ordre ne doit être envoyé à une place de marché réelle.
- Les cours peuvent être générés par un moteur de simulation ou alimentés par des
  données de démonstration.
- L'interface doit indiquer clairement qu'il s'agit d'un environnement DEMO.
- Les soldes affichés sont des crédits virtuels.
- Le projet sert à la démonstration, au développement et aux tests UX/techniques.

8. MOTEUR DE MARCHÉ SIMULÉ
================================================================

Le moteur de marché est le cœur de la simulation.

Il génère des variations de prix artificielles.

Exemple simplifié :

prix_actuel = prix_précédent * (1 + variation)

variation :
- petite variation aléatoire
- tendance éventuelle
- volatilité configurable
- événements simulés optionnels

Paramètres :
- volatility
- drift
- spread
- tick_interval_ms
- trading_hours
- market_status

MODES :
1. RANDOM
2. TREND
3. HISTORICAL_REPLAY
4. MANUAL_ADMIN

Le mode MANUAL_ADMIN permet à l'administrateur de définir un prix de
démonstration.

IMPORTANT :
Le moteur doit être isolé de toute API de courtier réelle.

11. PROCESSUS D'ACHAT
================================================================

Exemple :

Utilisateur choisit :
Asset = TECHX
Action = ACHETER
Quantité = 10
Type = MARKET

Le frontend demande au backend :

POST /api/orders

Le backend :

1. authentifie l'utilisateur
2. vérifie que l'actif existe
3. vérifie la quantité
4. récupère le prix simulé
5. calcule la valeur
6. calcule les frais simulés
7. vérifie le cash disponible
8. crée l'ordre
9. transmet l'ordre au moteur de simulation
10. reçoit le résultat d'exécution
11. met à jour le portefeuille
12. met à jour le cash
13. enregistre le trade
14. publie un événement WebSocket
15. retourne le résultat au frontend

================================================================
12. PROCESSUS DE VENTE
================================================================

Avant une vente :

1. Vérifier la position
2. Vérifier la quantité disponible
3. Calculer la valeur
4. Calculer les frais
5. Créer l'ordre
6. Simuler l'exécution
7. Diminuer la quantité détenue
8. Ajouter le produit de la vente au cash
9. Calculer le P&L réalisé
10. Enregistrer le trade

Une vente ne doit jamais permettre à l'utilisateur de vendre plus
d'unités qu'il n'en possède, sauf si le mode "short simulé" est
explicitement activé.

commission_fixed = 1.00 DEMO

quantité = 10

valeur = 1000

commission = 1.00

total achat = 1001.00

Ces frais sont purement fictifs.

La règle de calcul doit être côté backend et non uniquement côté frontend.

14. PORTEFEUILLE
================================================================

Une position contient :

- id
- user_id
- asset_id
- quantity
- average_entry_price
- current_price
- market_value
- unrealized_pnl
- unrealized_pnl_percent
- realized_pnl
- total_fees

Formules :

market_value =
quantity * current_price

unrealized_pnl =
(quantity * current_price)
-
(quantity * average_entry_price)

unrealized_pnl_percent =
unrealized_pnl /
(quantity * average_entry_price)
* 100

Le backend est la source de vérité.

41. MOTEUR DE SIMULATION — LOGIQUE
================================================================

Boucle :

TICK toutes les X millisecondes

Pour chaque actif :

1. récupérer prix
2. calculer variation
3. calculer nouveau prix
4. générer bid/ask
5. mettre à jour prix
6. enregistrer tick si nécessaire
7. vérifier les ordres limites
8. vérifier stop-loss
9. vérifier take-profit
10. exécuter les ordres déclenchés
11. publier PRICE_UPDATE

Pseudo-code :

while marketRunning:

    for asset in assets:

        oldPrice = asset.price

        movement = randomMovement(
            volatility=asset.volatility
        )

        newPrice = oldPrice * (1 + movement)

        updateAssetPrice(asset, newPrice)

        processOpenOrders(asset)

        processStopLoss(asset)

        processTakeProfit(asset)

        publishPriceUpdate(asset)

MARKET BUY :

execution_price =
ask_price + slippage

MARKET SELL :

execution_price =
bid_price - slippage

Le slippage doit rester fictif et configurable.

Paramètres :

min_slippage
max_slippage

================================================================
43. SPREAD
================================================================

Exemple :

mid_price = 100

spread = 0.04

bid = 99.98
ask = 100.02

BUY MARKET :
100.02

SELL MARKET :
99.98

Cette distinction rend le comportement plus réaliste.

================================================================
44. FRACTIONNEMENT DES ORDRES
================================================================

Optionnel mais recommandé.

Un ordre de 100 unités peut être exécuté :

40 unités à 100.10
30 unités à 100.12
30 unités à 100.15

Average fill :

(40*100.10 + 30*100.12 + 30*100.15) / 100

Le système crée trois trades liés au même order_id.

================================================================
45. P&L
================================================================

P&L latent :

current_value - cost_basis

P&L réalisé :

prix_vente - prix_achat
multiplié par quantité
moins frais

Pour une position :

cost_basis =
quantity * average_entry_price

market_value =
quantity * current_price

unrealized_pnl =
market_value - cost_basis

================================================================
67. RÈGLES MÉTIER PRINCIPALES
================================================================

RÈGLE 1
Un utilisateur ne peut dépenser plus que son cash disponible.

RÈGLE 2
Une vente ne peut dépasser la position disponible sauf mode short
explicitement activé.

RÈGLE 3
Les frais sont calculés côté serveur.

RÈGLE 4
Le frontend ne peut jamais définir directement un nouveau solde.

RÈGLE 5
Un ordre FILLED ne peut pas redevenir OPEN.

RÈGLE 6
Un ordre CANCELLED ne peut pas être exécuté.

RÈGLE 7
Chaque exécution crée une trace dans trades.

RÈGLE 8
Chaque variation financière crée une trace ledger.

RÈGLE 9
Les actions importantes sont auditées.

RÈGLE 10
Aucune connexion à un courtier ou système financier réel.

68. MACHINE À ÉTATS D'UN ORDRE
================================================================

CREATED
  |
  v
OPEN
  |
  +----> CANCELLED
  |
  +----> PARTIALLY_FILLED
              |
              v
           FILLED

Possibilité :
OPEN -> EXPIRED

Interdire :

FILLED -> OPEN
CANCELLED -> FILLED
EXPIRED -> FILLED
